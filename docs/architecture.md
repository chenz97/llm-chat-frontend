# Architecture

## High-Level Structure

The repository is a Next.js 16 App Router application with a browser-heavy runtime model. Most product behavior lives in client components and browser storage helpers. The only server runtime entry point is the optional forwarding route at `app/api/chat/completions/route.ts`.

Primary top-level directories:

- `app/`: App Router entry points, page shell, API route, and global CSS.
- `components/`: UI building blocks for chat, settings, rendering, and modal interactions.
- `lib/`: Request, storage, image, and error helper modules.
- `types/`: Shared TypeScript interfaces for settings, messages, and request payloads.
- `scripts/`: Local developer utility scripts. Current scope is a raw chat-completions debug helper.
- `public/`: Static assets generated by the default Next.js template.

## Runtime Composition

`app/page.tsx` is the client-side orchestration layer for the main screen. It owns:

- the active conversation object,
- selected API configuration, preset, and model override,
- settings modal visibility,
- mobile sidebar state,
- startup restoration logic,
- draft-conversation creation before first persistence.

The page composes four major UI areas:

- `components/ConversationSidebar.tsx`: loads saved conversations, supports keyword search, and handles deletion and selection.
- `components/ConversationConfigSelector.tsx`: surfaces current API config, preset, and model selection, filters the preset selector by preset visibility, and refreshes itself when settings change.
- `components/ChatInterface.tsx`: owns message rendering, composer state, multi-image draft handling, streaming lifecycle, throttled persistence, interruption finalization, editing, regeneration, and stop-generation behavior.
- `components/SettingsModal.tsx`: tab container for settings management.

## Settings Subsystem

`components/SettingsModal.tsx` exposes three settings surfaces:

- `components/ApiConfigManager.tsx`: CRUD UI for provider records.
- `components/AssistantPresetManager.tsx`: CRUD UI for reusable assistant presets, including default-preset selection, provider-scoped model filtering, per-preset request API selection, and per-preset main-selector visibility.
- `components/SettingsTransfer.tsx`: JSON import/export and manual GitHub Gist sync for API configs, presets, and the default preset pointer.

Settings screens communicate updates to the rest of the app through browser events such as `settingsUpdated` and `assistantPresetsMigrated`.

Settings transfer logic is split so the UI can share validation and remote-sync behavior:

- `lib/settingsTransferCore.ts`: versioned settings import normalization and the shared settings transfer constants.
- `lib/settingsTransfer.ts`: storage-backed settings export construction and normalized import persistence.
- `lib/githubGistSync.ts`: direct GitHub REST API calls for creating, updating, and reading the configured Gist file.

## Persistence Architecture

`lib/storage.ts` is the storage boundary for the application.

IndexedDB is the primary persistence layer and currently defines four object stores inside the `llm_chat_db` database:

- `api_configs`
- `conversations`
- `assistant_presets`
- `meta`

The `meta` store keeps small singleton values such as:

- `current_conversation_id`
- `default_preset_id`

GitHub Gist sync configuration is intentionally kept in `localStorage` under `llm_chat_settings_sync_config` rather than IndexedDB because it is a small browser-local integration preference. It contains the GitHub token, Gist ID, and target filename; it is not part of the settings export envelope.

Fallback behavior:

- API configurations and assistant presets can fall back to `localStorage`.
- assistant presets can be migrated from legacy `localStorage` storage into IndexedDB.
- conversations do not have a `localStorage` fallback path.

This storage module also exposes application-level operations such as `getCurrentConversationId`, `saveConversation`, `updateConversationMessages`, and `generateId`, so component code does not manipulate IndexedDB directly.

## Chat Request And Streaming Flow

The end-to-end chat path is split across `components/ChatInterface.tsx`, `lib/api.ts`, and optionally `app/api/chat/completions/route.ts`.

Flow for a normal message:

1. `ChatInterface` collects user text and zero or more uploaded image data URLs.
2. The component persists a pending assistant placeholder message so the conversation exists before streaming completes.
3. `ChatInterface` resolves the selected preset request API mode. Chat-completions presets build `messages` and prepend the preset system prompt as a system message, while Responses presets build `input` items, map the preset system prompt to `instructions`, and reuse the latest saved assistant `response.id` as `previous_response_id` when a valid Responses chain exists.
4. `lib/api.ts` emits one text item plus one image item per attached user image, targets either `/chat/completions` or `/responses`, and preserves the existing proxy-vs-direct transport choice.
5. `lib/api.ts` parses SSE `data:` lines, extracts assistant content, best-effort reasoning text, reasoning details, token usage, provider metadata, and Responses `response.id`, then feeds incremental callbacks back into `ChatInterface`. `ChatInterface` merges repeated reasoning-detail chunks into stable blocks, and later chat-completions requests normalize saved reasoning metadata again before replaying only assistant turns that completed normally and still carry the required signatures.
6. `ChatInterface` updates in-memory messages, throttles partial conversation persistence, flushes pending persistence when the page is backgrounded, and performs a final full save when streaming completes, is stopped, or fails mid-stream.

`app/api/chat/completions/route.ts` is intentionally narrow. It validates `baseUrl`, `apiKey`, and `request`, reads the preset-selected request API mode, resolves either the upstream `/chat/completions` or `/responses` endpoint, forwards the request server-side, and streams the upstream body back to the browser.

## Rendering Pipeline

Assistant messages are rendered through:

- `components/Message.tsx`: message shell, copy/edit/regenerate controls, usage display, raw-response access, and single or multi-image preview handling.
- `components/MarkdownRenderer.tsx`: markdown, math, syntax highlighting, and custom link/code rendering.
- `components/RawResponseModal.tsx`: modal for inspecting captured raw SSE lines.
- `components/ImageLightbox.tsx`: zoom and rotate controls for uploaded images.

The message renderer distinguishes user, assistant, and system roles and includes dedicated handling for assistant reasoning text, response metadata, and persisted interruption notices for failed or manually stopped streams.

## Styling And Layout

`app/globals.css` defines the shared visual system:

- layout utility classes such as `.app-shell` and `.app-panel`,
- global color variables,
- animations for shell and message entry,
- markdown typography rules,
- custom scrollbars.

`app/layout.tsx` applies Geist Sans and Geist Mono as application fonts and sets the root metadata for the Next.js app shell.

## Developer Utilities

`scripts/debug_chat_completion.py` mirrors the frontend chat-completions endpoint-resolution logic and forces `stream: true` so a developer can inspect raw upstream responses outside the browser. This is useful when diagnosing provider-specific network failures or malformed streaming payloads.
