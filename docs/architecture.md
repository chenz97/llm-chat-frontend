# Architecture

## High-Level Structure

The repository is a Next.js 16 App Router application with a browser-heavy runtime model. Most product behavior lives in client components and browser storage helpers. The only server runtime entry point is the optional forwarding route at `app/api/chat/completions/route.ts`.

Primary top-level directories:

- `app/`: App Router entry points, page shell, API route, and global CSS.
- `components/`: UI building blocks for chat, settings, rendering, and modal interactions.
- `lib/`: Request, storage, image, and error helper modules.
- `types/`: Shared TypeScript interfaces for settings, messages, and request payloads.
- `scripts/`: Local developer utility scripts. Includes a raw chat-completions debug helper and an isolated browser memory regression check.
- `public/`: Static assets generated by the default Next.js template.

## Runtime Composition

`app/page.tsx` is the client-side orchestration layer for the main screen. It owns:

- the active conversation object,
- selected API configuration, preset, and model override,
- settings modal visibility,
- mobile sidebar state,
- startup restoration logic,
- draft-conversation creation before first persistence.

The page can also be opened with chat deep-link parameters that are consumed by
`components/ChatInterface.tsx` after startup restoration is complete. The
supported parameters are `prompt=<text>` for filling the composer and
`autoSend=1` for immediately sending that prompt through the normal chat submit
flow.

The page composes four major UI areas:

- `components/ConversationSidebar.tsx`: loads conversation summaries from a persistent search index, supports keyword search, and handles deletion and selection.
- `components/ConversationConfigSelector.tsx`: surfaces current API config, preset, and model selection, filters the preset selector by preset visibility, and refreshes itself when settings change.
- `components/ChatInterface.tsx`: owns message rendering, composer state, multi-image draft handling, streaming lifecycle, voice-call recording/playback lifecycle, throttled persistence, interruption finalization, editing, regeneration, and stop-generation behavior.
- `components/SettingsModal.tsx`: tab container for settings management.

## Settings Subsystem

`components/SettingsModal.tsx` exposes three settings surfaces:

- `components/ApiConfigManager.tsx`: CRUD UI for provider records.
- `components/AssistantPresetManager.tsx`: CRUD UI for reusable assistant presets, including default-preset selection, provider-scoped model filtering, per-preset request API selection, and per-preset main-selector visibility.
- `components/SettingsTransfer.tsx`: JSON import/export and manual end-to-end encrypted GitHub private-repository sync for API configs, presets, and the default preset pointer.

Settings screens communicate updates to the rest of the app through browser events such as `settingsUpdated` and `assistantPresetsMigrated`.

Settings transfer logic is split so the UI can share validation and remote-sync behavior:

- `lib/settingsTransferCore.ts`: versioned settings import normalization and the shared settings transfer constants.
- `lib/settingsTransfer.ts`: storage-backed settings export construction and normalized import persistence.
- `lib/settingsCrypto.ts`: browser-side AES-256-GCM encryption of the settings payload with a PBKDF2-SHA-256 (600k iterations) passphrase-derived key.
- `lib/githubRepoSync.ts`: GitHub Contents API calls that verify the target repository is private, then create, update, or read the encrypted settings file.
- `lib/settingsSyncConfig.ts`: local sync configuration normalization shared by the encrypted sync UI.
- `lib/floatingStatus.ts` and `components/FloatingStatus.tsx`: browser event and UI surface for floating success or error notifications inside the settings modal.

`components/SettingsModal.tsx` listens for floating status events so nested settings tabs can report operation outcomes without each tab owning its own overlay lifecycle.

## Persistence Architecture

`lib/storage.ts` is the storage boundary for the application.

IndexedDB is the primary persistence layer and uses schema version 4 and defines five object stores inside the `llm_chat_db` database:

- `api_configs`
- `conversations`
- `conversation_index`
- `assistant_presets`
- `meta`

`lib/conversationIndex.ts` builds metadata and normalized title/message search text. The version 4 upgrade visits existing conversations individually to populate the index. Conversation writes and deletions update both stores in one transaction. Sidebar and startup reads return summaries without messages, media, diagnostic logs, or search text. Full histories are loaded only when selected.

The `meta` store keeps small singleton values such as:

- `current_conversation_id`
- `default_preset_id`

Encrypted GitHub sync configuration is intentionally kept in `localStorage` under `llm_chat_settings_sync_config` rather than IndexedDB because it is a small browser-local integration preference. It contains the GitHub token, repository (`owner/repo`), and file path (the encryption passphrase is never persisted); it is not part of the settings export envelope.

Fallback behavior:

- API configurations and assistant presets can fall back to `localStorage`.
- assistant presets can be migrated from legacy `localStorage` storage into IndexedDB.
- conversations do not have a `localStorage` fallback path.

This storage module also exposes application-level operations such as `getCurrentConversationId`, `saveConversation`, `updateConversationMessages`, and `generateId`, so component code does not manipulate IndexedDB directly.

## Chat Request And Streaming Flow

The end-to-end chat path runs through `components/ChatInterface.tsx`, `lib/responsesRequest.ts` for Responses request construction, `lib/api.ts` for streaming, and optionally `app/api/chat/completions/route.ts` for forwarding.

`lib/chatDeepLink.ts` contains the parser for URL-driven chat actions. It
normalizes `prompt` and `autoSend` from either query string or hash parameters,
ignores empty prompts, and lets query-string values take precedence over hash
values. `ChatInterface` applies the parsed action once per page load only after
both the active conversation and API configuration are available.

Flow for a normal message:

1. `ChatInterface` collects user text and zero or more uploaded image data URLs.
2. The component persists a pending assistant placeholder message so the conversation exists before streaming completes.
3. `ChatInterface` resolves the selected preset request API mode. Chat Completions sends `messages` with the preset system prompt as a system message. Responses sends `input` with the preset system prompt as `instructions`. OpenRouter Responses requests include the full conversation history. Other Responses providers use `previous_response_id` and incremental input when the latest assistant message has a saved response ID.
4. Both request builders emit one text item plus one image item per attached user image. `lib/api.ts` sends the body to `/chat/completions` or `/responses`, either directly or through the server proxy. If a Responses endpoint returns HTTP 400 reporting that `previous_response_id` is unsupported, `lib/api.ts` retries with the conversation history.
5. `lib/api.ts` parses SSE `data:` lines, extracts assistant content, best-effort reasoning text, reasoning details, token usage, provider metadata, and Responses `response.id`, then feeds incremental callbacks back into `ChatInterface`. `ChatInterface` merges repeated reasoning-detail chunks into stable blocks, and later chat-completions requests normalize saved reasoning metadata again before replaying only assistant turns that completed normally and still carry the required signatures.
6. `ChatInterface` updates in-memory messages, serializes partial conversation writes and keeps only the latest queued update, flushes pending persistence when the page is backgrounded, and performs a final full save when streaming completes, is stopped, or fails mid-stream.

Flow for a voice-call turn:

1. `ChatInterface` enters call mode from the composer, loads the browser VAD assets from `public/vad/`, requests microphone access through the VAD library, and shows the current call state.
2. While the call state is listening, the VAD classifies microphone PCM frames. Speech start moves the UI to recording; speech end returns a 16 kHz `Float32Array` segment that already includes configured pre-speech and trailing redemption padding.
3. The VAD-produced PCM segment is encoded into a mono 16-bit WAV base64 `AudioRecord` before it is saved or sent upstream, because Chat Completions `input_audio` supports `wav` and `mp3`.
4. If the VAD dependency or local assets cannot initialize, `ChatInterface` falls back to the earlier Web Audio analyser plus `MediaRecorder` path, where periodic RMS volume checks start recording and 3 seconds below the threshold submits the segment.
5. `lib/audioChat.ts` builds a streaming Chat Completions request with `modalities: ["text", "audio"]`, audio settings supplied through preset Model Parameters, the preset system prompt, text history, prior user audio history, and the current user audio.
6. The optional proxy route forwards this streaming audio request through the same route used by text streaming, while `lib/audioChat.ts` parses audio-specific SSE chunks.
7. The returned assistant text and audio are saved as a normal assistant message with audio records. The browser plays the assistant audio, then resumes VAD listening if call mode is still active.

`app/api/chat/completions/route.ts` is intentionally narrow. It validates `baseUrl`, `apiKey`, and `request`, reads the preset-selected request API mode, resolves either the upstream `/chat/completions` or `/responses` endpoint, forwards the request server-side, and streams the upstream body back to the browser.

## Rendering Pipeline

Assistant messages are rendered through:

- `components/MessageList.tsx`: initially mounts the latest 40 messages and reveals earlier history in batches of 40 while preserving the scroll position.
- `components/Message.tsx`: message shell, copy/edit/regenerate controls, usage display, raw-response access, audio replay controls, and single or multi-image preview handling.
- `components/MarkdownRenderer.tsx`: memoized markdown, math, syntax highlighting, and custom link/code rendering.
- `components/RawResponseModal.tsx`: modal for inspecting captured SSE diagnostics, bounded by `lib/rawResponse.ts` with audio payload omission.
- `lib/audioPlayback.ts`: chunked base64 encoding and Blob construction shared by call playback and message replay.
- `components/ImageLightbox.tsx`: zoom and rotate controls for uploaded images.

The message renderer distinguishes user, assistant, and system roles and includes dedicated handling for assistant reasoning text, response metadata, and persisted interruption notices for failed or manually stopped streams.

## Styling And Layout

`app/globals.css` defines the shared visual system:

- global color and radius variables, including a blue accent (`--accent` #2563eb) used for primary actions, the active conversation, focus states, and brand marks,
- layout classes (`.app-shell`, `.app-sidebar`, `.chat-column`) in the Tailwind `components` layer so utilities can still override them,
- reusable control classes (`.ui-input`, `.ui-label`, `.ui-btn` with `-primary`/`-secondary`/`-ghost`, `.ui-icon-btn`, `.ui-card`, `.ui-chip`) used by the sidebar, composer, and settings forms,
- hover-revealed message actions (`.message-actions`, always visible on touch devices) and the streaming typing indicator,
- markdown typography, code-block header, and table wrapper rules,
- thin custom scrollbars.

The layout is a flat full-height sidebar (conversation list plus a compact current-assistant footer that opens a popover with the API, preset, and model selectors) plus a chat area whose messages and composer share a centered reading column. On narrow or portrait screens the sidebar becomes a slide-in drawer opened from a compact header. The visual layer avoids `backdrop-filter`, background gradients, and whole-page entrance animations to keep paint and GPU cost low; message entry uses an opacity-only fade. Assistant reasoning is expanded while streaming and collapses afterwards, and collapsed reasoning is not rendered.

`app/layout.tsx` applies Geist Sans and Geist Mono as application fonts and sets the root metadata for the Next.js app shell.

## Developer Utilities

`scripts/debug_chat_completion.py` mirrors the frontend chat-completions endpoint-resolution logic and forces `stream: true` so a developer can inspect raw upstream responses outside the browser. This is useful when diagnosing provider-specific network failures or malformed streaming payloads.

`scripts/check_browser_memory.mjs` uses Chrome remote debugging and synthetic IndexedDB histories to verify schema upgrades, search, writes, long-message pagination, and retained JavaScript heap. It requires a disposable profile and explicit `MEMORY_CHECK_ALLOW_RESET=1`, because it resets the test origin database.
